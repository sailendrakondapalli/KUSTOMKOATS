# Backend Production-Readiness Audit

Scope: the Supabase backend (Postgres schema and RLS, Storage policies, and the Deno edge functions), plus how the React app calls it. The audit read the frontend and changed none of it. **Integration update (2026-10-18):** a parallel frontend change has since added the admin guard; where this report says the admin UI is unauthenticated, read it as "until the frontend change is deployed". Combined status and rollout order: `docs/production-readiness-summary.md`. Audit date: 2026-10-18. OpenSpec change: `openspec/changes/backend-production-readiness/`.

Status legend: **FIXED** (implemented and verified in this change), **PARTIAL**, **PROPOSED** (written down but not applied because it needs approval), **OPEN**.

## 1. Current architecture and stack

| Concern | Actual implementation (evidence) |
|---|---|
| Runtime / API | No custom server. The browser calls Supabase PostgREST directly through `@supabase/supabase-js` with the public anon key (`src/lib/supabase.js`). There are about 60 `.from()` and `.rpc()` call sites. |
| Edge functions | Deno on Supabase Edge Runtime, in `supabase/functions/*`: `create-razorpay-order`, `verify-razorpay-payment`, `razorpay-webhook`, `create-shiprocket-order`, `eway-bill-proxy`. Before this change they used `std@0.168.0/http/server.ts` and an unpinned `esm.sh/@supabase/supabase-js@2`. |
| Database | Supabase Postgres **17.6.1.166**, the version recorded by the Supabase CLI link metadata. There is no ORM. Authorization is done only with RLS policies and `SECURITY DEFINER` functions and triggers. |
| Migrations | Before this change there was **no migration tool in use**. There are 32 hand-run root `*.sql` scripts ("run this in the SQL editor"). Some overlap, some contradict each other, and several are not idempotent. There was no `supabase/config.toml` and no `supabase/migrations`. |
| Async / outbound HTTP | `pg_net` from SQL (`eway-bill-proxy-function.sql`). There are no queues, cron jobs, or cache. |
| Integrations | Razorpay (orders, checkout signature, webhook), Shiprocket (adhoc order), the GST e-way-bill API, and Supabase Storage (`product-images`, `images`). |
| Deployment | The frontend deploys to Vercel (`vercel.json`). Functions are deployed by hand with `supabase functions deploy` (per the root `*-SETUP.md` docs). Schema changes are pasted into the SQL editor. There is no CI. |
| Tests | None existed for the backend. |

## 3. Prioritized remediation

- **P0.** BE-003 is done. BE-001, BE-002 and BE-004 need **owner approval and frontend work**. Until then the system should not be considered production-safe, whatever else is fixed.
- **P1.** BE-005 and BE-009 are done. BE-006, BE-007, BE-010 and BE-011 are partly done. BE-008 is proposed.
- **P2.** BE-012, BE-013, BE-015 and BE-017 are done. BE-016 is partly done. BE-014 and BE-018 are open or proposed.
- **P3.** BE-019 and BE-020 are partly done.

## 4. Gap summary by area

- **Security:** BE-001/002/004/007/008/011/014/018 dominate. Every effective control lives in RLS, so the proposed lockdown migration is the main lever. It can't be applied until the frontend admin guard (FE-001, now implemented) is deployed and every admin has `app_metadata.role = 'admin'`. The guard's transitional email allow-list (FE-017) grants UI access only; allow-listed users without the role will get failed writes after the lockdown. Guest checkout was also adjusted so it no longer reads its order back after insert, which the lockdown's `own or admin read` policy would have rejected.
- **API:** The edge-function contracts (`{ success, order | shipment | error }`) are preserved. The status codes changed only on error paths: upstream failures now return 502, a missing order returns 404, and validation failures return 400. The webhook now returns 200 for unknown orders.
- **Reliability:** Payment transitions and stock deduction are now idempotent, and upstream calls have timeouts. There are no background jobs, so stuck `pending` orders depend on the webhook. A reconciliation job is a future option (section 7).
- **Scalability:** The traffic is small-business scale. The indexes added under BE-013 cover the hot paths (webhook lookup, per-user orders, admin listing). There is no evidence that a cache or queue is needed, so none was added.
- **Testing:** See `docs/backend-operations.md` §Testing for what exists and how to run it.

## 5. Database schema and migration audit

- **History.** The 32 root scripts are the only record, and they conflict. For example, `setup-product-bundles.sql` and `product-bundles-schema.sql` define different bundle-link tables (`product_bundles` and `product_bundle_relations`). `testimonials-schema.sql` is non-idempotent (bare `CREATE POLICY`). `pos-sales-setup.sql` and `fix-place-location.sql` fail on a fresh DB because they reference columns no script creates. Diagnostics and data patches are mixed in (`check-pending-payments.sql`, `fix-expired-promo-codes.sql`, `diagnose-eway-bill.sql`, which also makes an outbound HTTP call).
- **New layout.** The migration files are in `supabase/migrations/` and use the Supabase CLI convention `<UTC timestamp>_<name>.sql`:
  1. `20261018000000_baseline_repo_schema.sql` reconstructs the last-writer-wins state of the repo scripts. It is for **fresh or dev environments only**. On production, mark it applied instead (`supabase migration repair --status applied 20261018000000`) after reviewing a `supabase db dump`.
  2. `20261018000100_reconcile_schema_drift.sql` adds the columns the app uses with `IF NOT EXISTS`, plus an `orders.updated_at` trigger. It is additive and nullable, so it costs only a metadata lock.
  3. `20261018000200_integrity_constraints_indexes.sql` adds `NOT VALID` checks with a guarded `VALIDATE`, adds indexes, and adds unique indexes only when there are no duplicates (otherwise it raises a `NOTICE`).
  4. `20261018000300_payment_stock_hardening.sql` adds `is_admin()`, the `stock_deducted_at` guard and backfill, the shortfall notifications, the definer `search_path` fix, and drops the forged-notification insert policy.
  5. `supabase/proposed/20261018100000_PROPOSED_admin_rls_lockdown.sql` is **not applied**. It requires approval (section 6).
- **Safety.** Every applied migration is additive or reversible and idempotent. None drops a table, column or data. They run in the CLI's per-file transaction, so they use no `CONCURRENTLY`. The tables are small, but `CREATE INDEX` takes a `SHARE` lock, so run it at a low-traffic time.
- **Verification.** The migrations were run in a throwaway `supabase/postgres:17.6.1.166` container, which is the same version as production. This covered a fresh install, a simulated upgrade path (legacy root scripts first, then migrations 0100–0300), an idempotent re-run, behavioural tests, and RLS tests of the proposal. See `supabase/tests/db/` and the results in the OpenSpec `tasks.md`.
- **Limitations.** The production schema was **not inspected**, as the rules required. Drifted objects (BE-010 and BE-014) could differ in type or definition. The test environment stubs `auth.jwt()` and `storage.*`, which the Supabase services normally provide.

## 6. Requires approval (not applied)

1. **Admin RLS lockdown** (BE-001/002/007/008/011/018): `supabase/proposed/20261018100000_PROPOSED_admin_rls_lockdown.sql`. It **breaks the current unauthenticated admin panel**. Prerequisites: the frontend admin guard deployed (implemented in `frontend-production-readiness`), and admin users granted `app_metadata.role = 'admin'` through the service role. See the ordered checklist in `docs/production-readiness-summary.md`.
2. **Server-side order creation and pricing** (BE-004): this is a **breaking API change** to the checkout and POS flows.
3. **Private payment-proof bucket** (BE-008): this changes the frontend upload path.
4. **Rotating the e-way-bill password and moving it to Vault** (BE-002): an irreversible operational action.
5. **Marking the baseline as applied on production** (`migration repair`): this changes the production migration history table.

## 7. Docker, deployment and external dependencies

- **Production containers don't apply.** Postgres, PostgREST, Auth, Storage and the Edge Runtime are managed by Supabase, and the SPA is hosted on Vercel. There is no backend process to containerize, and a self-built image would not be what runs in production. The root `Dockerfile` belongs to the frontend change.
- **What this change adds.** `supabase/tests/compose.yaml` defines a throwaway Postgres pinned to the production version, plus a Deno test runner. It is used for migration and RLS tests, and it never connects to the live project.
- **Migration execution.** Migrations run once per release from a single controlled place (an operator or a CI job running `supabase db push`). They are never run by app replicas. The order is: apply the DB migrations, then deploy functions, then deploy the frontend. This expand-before-use order is described in `docs/backend-operations.md`.
- **External dependencies.** Razorpay (with a 10 s timeout; failures return 502 and the webhook reconciles later), Shiprocket (cached token; failures don't block checkout), and the GST e-way-bill API.
- **Graceful shutdown.** Supabase Edge Runtime manages worker lifecycle. The handlers are stateless and their outbound calls have timeouts, so an evicted worker can't hang a request indefinitely.

## 8. Unresolved risks

- BE-001, BE-002 and BE-004 remain exploitable in production until the approvals in section 6 are acted on.
- The definitions of the drifted RPCs and tables are unknown (BE-010/014).
- If the Razorpay API is down, verification returns 502 even though the customer has paid. The webhook marks the order paid later, so the customer may see a "contact support" toast in the meantime.
- Existing duplicate `razorpay_order_id` or `display_order_id` values in production would leave the unique indexes uncreated, and the migration logs a `NOTICE`. Check this after applying.
